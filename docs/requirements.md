# 软件项目全生命周期管理桌面应用 · 需求梳理

版本：v0.4（讨论稿，2026-10-20）
说明：v0.1 是"个人项目台账"方向；v0.2 根据"需求列表 → 客户沟通细化 → 功能设计 → 排期 → 需求变更"重写；v0.3 按 2026-10-20 的讨论结论调整；v0.4 采纳实际开发日期方案，页面级规格见 [mvp-pages.md](mvp-pages.md)。**v0.3 起的结论优先于下文对应条目**。

## v0.3 讨论结论（覆盖下文相关条目）

已确认的前提：

1. **单用户、多项目、不登录**：不做账号、权限、客户门户；客户只看你截图或导出的内容。
2. **项目内集中排期**：每个项目有一个独立的"排期"页，把该项目所有待排期需求集中在一个页面，批量分配到版本或日期；不做跨项目排期总表，也不做甘特图。工作台只汇总各项目的版本节点。
3. **变更确认以微信/口头为主**：不要求客户签字，不做审批流。变更单主要给自己留档，同时提供适合截图的客户视图；记录确认渠道、时间、备注，并附微信截图。
4. **三种"部分删除"都要支持**：
   - 需求内删减一部分内容 → 修改描述/验收标准，保留修改前后版本；
   - 删除一个子功能 → 父子需求，取消子需求；
   - 大需求拆分后删掉其中一条 → 拆分功能，取消其中一个子需求。
   因此**需求层级与拆分进入 P0**；合并放 P1。
5. **附件**：需求、沟通记录、变更单都支持多个附件；文件复制到应用数据目录，图片可预览，其他文件调用系统程序打开；备份包含附件。
6. **验收和正式交付暂不做**：MVP 不建验收清单/签收/交付报告；需求状态可以跳过"待验收"，从"开发中"直接到"已完成"；变更详情的客户视图用于截图即可。
7. **变更状态简化**：草稿 / 待确认 / 已确认 / 已生效 / 已取消；客户不同意时取消并记录原因，不做单独的"已拒绝"审批分支。
8. **MVP 默认细节**：需求层级按三层设计（需求 → 模块 → 子功能），数据模型用 `parent_id` 递归、界面支持三层；叶子节点承载状态/预估/版本/实际日期，父节点汇总；附件单文件上限 50MB，图片内联预览，其他文件调用系统程序打开；变更客户视图默认隐藏成本、风险、内部备注。

对 MVP 的影响：

- **增加**：需求层级/拆分、附件、集中排期页、变更单客户视图。
- **移除**：验收清单与签收、正式交付报告/PDF、变更审批流。
- **调整**：需求状态枚举保留"待验收"但 MVP 可跳过；正式导出降为 P1，P0 只保留截图友好的详情页。
- **工期**：预计增加 1~2 周，MVP 约 8~10 周（每天 2~4 小时）。

仍需确认：项目内排期按"版本/里程碑"还是"周/具体日期"分组；MVP 默认批量分配，拖拽放 P1。详见第 14 节。

## v0.3.1 版本归属与开发时间（已采纳，2026-10-20）

### 需求属于哪个版本

- 需求表增加 `release_id`（可空；为空表示"待排期"）。
- **一个需求同一时间只属于一个版本**；如果一条需求要跨版本交付，用 P0 的拆分功能拆成子需求，分别归属。这样"属于哪个版本"永远只有一个答案。
- 三个入口建立归属：
  1. 需求详情：顶部"所属版本"下拉，显示版本名和起止日期；
  2. 需求列表：版本列内联选择；
  3. 项目排期页：勾选多条需求 → 批量分配到版本。
- 版本详情页反向列出该版本的全部需求，作为归属的最终确认；需求详情和版本详情必须能互相跳转。
- 每次归属变化写入活动记录：原版本 → 新版本、时间、备注。
- 一致性规则：
  - 需求状态改为"已排期"时必须绑定版本，否则提示先选择版本；
  - 版本必须设置起止日期，否则排期页显示"未设置日期"并提醒；
  - 已发布版本中的需求移入/移出需要填写原因（P1 可加锁定）。

### 什么时间开发的

分"计划时间"和"实际时间"两层，避免把"计划"和"实际"混为一谈：

| 类型 | 来源 | 展示 |
| --- | --- | --- |
| 计划开发时间 | 所属版本的起止日期 | 需求详情显示 `V1.0 · 2026-10-20 ~ 2026-11-10` |
| 更细的计划时间 | 需求可选字段 `planned_start` / `planned_end` | 需要按周/按天排时再启用 |
| 实际开发时间 | 状态变化自动记录 | 需求详情显示 `实际：2026-10-22 ~ 2026-10-28（历时 7 天）` |

**实际开始/完成日期的规则：**

- `dev_started_at`：第一次进入"开发中"的时间；
- `dev_completed_at`：最近一次进入"已完成"的时间；
- 如果需求从"已完成"回退到"开发中"，清空完成日期、保留历史；再次完成时更新为新的完成时间，开始日期不变；
- 如果直接标记"已完成"但从未"开发中"，自动把开始日期补为完成日期，并提示可修改；
- 日期存 ISO 时间戳，界面按"年-月-日"显示；手动修改日期只改日期，不改状态；
- 所有自动写入和手动修改都写活动记录，便于追溯。

- 需求详情顶部显示：计划窗口（所属版本）+ 实际开发起止 + 历时天数；
- 需求列表增加"开发开始/完成"两列（默认隐藏，可开启），支持按这两列排序和筛选；
- 快速操作提供"开始开发""完成"两个一键按钮，降低忘记更新状态的概率；
- 版本详情展示：计划窗口、实际开发区间（未完成需求的最早开始 ~ 已完成需求的最晚完成）、完成数/总数；
- 父需求（有子需求时）的实际日期按子需求汇总：最早开始、最晚完成；
- 暂停/恢复的每次状态变化都写活动记录，时间线保留完整过程；MVP 的"历时"按自然日计算，不扣除非工作日，也不计算净工时；
- **工时（小时）暂不做**；如果后续需要，再加 `actual_hours` 和计时功能。

## v0.3.2 三层需求层级规则（已采纳，2026-10-21）

### 层级定义

```
L0 需求 Requirement
  └─ L1 模块 Module
       └─ L2 子功能 Sub-feature
```

- 数据模型用 `parent_id` 递归，`depth` 记录层级；界面 MVP 支持三层。
- L2 子功能在 MVP 中不再允许继续拆分；后续需要更深层级时再放开。
- 不是每条需求都必须有子节点；没有子节点的节点就是叶子，可以正常排期和开发。

### 叶子节点 vs 父节点

| 节点类型 | 状态 | 预估 | 版本 | 实际开发日期 | 描述/设计/附件 |
| --- | --- | --- | --- | --- | --- |
| 叶子（无子节点） | 可编辑 | 可编辑 | 可分配 | 自动/可改 | 可编辑 |
| 父节点（有子节点） | 汇总显示 | 汇总显示 | 汇总显示 | 汇总显示 | 可编辑，作为汇总说明 |

**为什么要这样分**：如果父节点和子节点都能独立改状态、版本、预估，很快会出现"父需求已完成、子功能还在开发"这类矛盾。让叶子承载真实数据、父节点只做汇总，数据只有一处来源。

### 汇总规则

| 字段 | 父节点显示 |
| --- | --- |
| 状态 | 全部取消 = 已取消；全部完成 = 已完成；有开发中 = 开发中；有已排期/进行中 = 进行中；否则取最靠前的未完成状态。状态徽标标注"汇总" |
| 预估 | 所有非取消叶子的预估之和 |
| 版本 | 所有非取消叶子同一版本 = 显示该版本；不同 = "跨版本"；有未排期 = "部分未排期" |
| 实际开发日期 | 最早开始 ~ 最晚完成；有未完成叶子时完成列留空并显示"进行中" |
| 进度 | 已完成叶子数 / 非取消叶子总数，如 `3/5` |

### 排期规则

- 版本只分配到**叶子**；父节点版本是汇总结果，不直接编辑。
- 在排期页选中父节点分配版本时，默认把版本应用到它所有非取消叶子，操作前给出确认提示。
- 版本统计只计算叶子，避免父子重复计数；同时显示"涉及 X 条需求"（不同 L0 祖先的数量）。

### 拆分规则

- L0 拆分 → 生成 L1 模块；L1 拆分 → 生成 L2 子功能；L2 在 MVP 不允许再拆。
- 拆分弹窗填写子项标题和预估，默认总预估等于原需求预估。
- 子项默认继承父节点当前的版本。
- 拆分只允许发生在开发开始之前（草稿/澄清中/已确认/设计中）；已经"开发中"的需求请新增子需求，而不是拆分，避免实际开发日期归属混乱。
- 拆分后父节点变成汇总节点，原描述保留为汇总说明，原预估变为只读汇总。

### 取消与变更

- 取消父节点会级联取消所有后代，操作前二次确认；所有节点保留历史，填写同一个取消原因。
- 变更项可以指向任意层级；如果指向父节点且发生级联，变更详情显示"影响 N 个子项"。
- 三种"部分删除"的落点：
  1. 删验收点 → 修改叶子内容，保留版本差异；
  2. 删子功能 → 取消 L2 叶子；
  3. 拆大需求后删一条 → L0 拆成 L1，再取消其中一个 L1（连带其 L2）。
- 合并放 P1。

### 列表与筛选

- 需求台账用树形表格，三层缩进、展开/折叠；父节点加粗，显示进度条和汇总版本。
- 按状态/版本筛选时，命中叶子后同时显示其祖先路径（祖先置灰），保证层级上下文不丢。

## v0.5 模型变更（已采纳，2026-10-21）

- 原“客户 Client”实体改名为“干系人 Stakeholder”。
- 项目与干系人改为多对多，通过 `project_stakeholders` 关联；一个项目可以有 0~N 个干系人。
- 项目表单支持多选干系人，项目列表展示多个干系人姓名。
- 文中后续出现的“客户”如果指项目关联实体，一律按“干系人”理解；作为需求提出方/沟通对象的业务角色仍可称客户。
- 干系人增加公司、多个联系方式；角色不再挂在干系人上，而是挂在“项目—干系人”关联上，同一干系人在不同项目可以有不同的角色。
- 迁移 v9 增加 `stakeholders.role`，v10 增加 `company`，v11 把旧角色代码转成文本，v12 创建 `stakeholder_contacts`，v13 迁移旧 `phone`，v14 给 `project_stakeholders` 增加 `role`，v15 把旧的干系人全局角色迁移到项目关联。
- 当前数据库中的 `projects.client_id`、`stakeholders.contact`、`stakeholders.phone`、`stakeholders.role` 保留为未使用的遗留列，后续重建表时再清理。

## 0. 一页纸总结

**定位**：面向个人开发者或小团队的本地化**需求与交付台账**。以需求为主线，管理一个软件项目从需求收集、客户澄清、功能设计、版本排期，到开发验收和需求变更的全过程。

**它要解决的核心问题**：任何一个时间点，都能回答下面六个问题——

1. 最初和客户确认的需求是什么？
2. 现在的需求范围变成了什么样？
3. 哪些是后来新增的、哪些被修改过、哪些被删除或缩减了？
4. 每次变化是谁提出的、为什么改、影响了多少工期和范围？
5. 客户是否确认过、什么时候、以什么方式确认的？
6. 当前这个版本计划交付哪些需求？

**它不做什么**：不做 Jira 式的研发管理（迭代燃尽、测试用例、CI/CD、代码仓库管理），不做多人协作和云同步。它管的是"需求及其变化"，不是"每一行代码和每一个测试"。

**MVP 一句话**：一个离线桌面应用，能维护客户/项目/需求台账，记录沟通和变更，把需求排进版本，并随时导出客户能看懂的需求清单和变更单。

**成功标准**：
- 客户说"这个之前不是说好了吗"时，30 秒内能翻出原始需求和当时的确认记录；
- 客户改需求时，能当场记录变更、评估影响，并生成一份变更单；
- 每周排期时，能看清每个版本有哪些需求、预估工作量多少、哪些还没确认；
- 项目结束时，能导出完整的"原始需求 → 变更 → 最终交付"对照。

## 1. 背景与痛点

### 1.1 当前的工作方式

需求通常散落在这些地方：客户微信聊天、会议记录、Excel 需求列表、Word 需求文档、原型图、脑子里。开发和交付过程中，需求会不断变化，但这些变化往往只存在于聊天记录里。

### 1.2 具体痛点

1. **原始范围说不清**：项目做久了，没人记得第一版确认了什么。客户觉得"这本来就有"，你记得"后来加的"，但没有证据。
2. **变更没有台账**：新增需求、修改需求、删除/缩减需求混在一起，工期为什么延长说不清。
3. **沟通结论丢失**：会议里确认的细节、微信里答应的调整，没有落到具体需求上，过两周就失真。
4. **需求、设计、排期脱节**：需求文档是一份，设计稿是另一份，排期表又是第三份，互相对不上。
5. **"部分删除"最难处理**：客户不是整条取消，而是"这个功能里第三点不要了"，原有的需求文本被改掉后，历史就消失了。
6. **交付文档靠手工整理**：每次给客户发需求确认单、变更单、进度报告，都要重新拼 Excel/Word。
7. **现有工具不合适**：Jira/Azure DevOps 太重，配置成本高；Excel/Notion 灵活但没有需求版本、变更、基线的概念，容易变成一堆散表。

### 1.3 为什么值得自己做一个桌面应用

- 数据在本地，客户资料和项目信息不经过第三方云；
- 可以完全按"个人接项目"的流程设计，而不是适配大公司的研发流程；
- 可以生成固定格式的客户交付文档；
- 离线可用，不依赖订阅和网络。

## 2. 产品目标与非目标

### 2.1 目标

1. **需求可追溯**：每条需求有稳定编号、当前内容和完整历史版本，任何修改都不覆盖旧内容。
2. **变更可管理**：新增、修改、删除、缩减范围都能被记录、评估影响、关联客户确认，并汇总成变更单。
3. **沟通有落点**：每次沟通记录能关联到具体需求或变更，结论和待办不丢失。
4. **排期有依据**：需求能分配到版本/里程碑，能看到每个版本的需求清单和预估工作量。
5. **交付有文档**：能按项目、版本或基线导出需求清单、变更单、范围对比。
6. **本地可控**：离线、单机、数据可导出、自动备份。

### 2.2 非目标（v1 明确不做）

- 多人协作、成员权限、评论、通知
- 客户端登录或客户门户
- 云端同步、账号体系
- 测试用例管理、缺陷跟踪、CI/CD、代码仓库管理
- 甘特图、资源排期、关键路径
- 合同、报价、回款管理（变更影响里可以记录费用，但不做财务系统）
- 与微信/邮箱/飞书自动同步（沟通记录手动录入）
- 移动端

## 3. 用户、假设与使用场景

### 3.1 用户假设（待确认）

- **单用户**：只有你（或你的小团队内部）使用，客户不登录系统。
- **交付方式**：给客户的确认单、变更单、进度报告通过导出文档发送。
- **项目数量**：同时维护 1~10 个客户项目，每个项目几十到几百条需求。
- **流程灵活**：不是所有项目都严格走完整流程，小项目可以只用到需求台账 + 沟通记录。

### 3.2 核心场景

**场景 A：接新项目，整理初始需求**
新建客户和项目 → 把客户发来的需求列表批量录入 → 逐条澄清、补充验收标准 → 标记"已确认" → 形成初始基线。

**场景 B：客户提出新需求**
客户微信说"再加一个导出 Excel 的功能" → 新建变更单，类型"新增" → 填写原因、影响工期 → 关联到项目/版本 → 客户确认 → 生效，需求进入台账。

**场景 C：客户修改或删减需求**
客户说"这个功能里的第三点不要了" → 打开原需求 → 发起变更（类型"缩减范围"）→ 修改需求内容和验收标准 → 系统保留修改前后的差异 → 变更单记录原因和确认方式 → 生效后基线对比能看出删了什么。

**场景 D：每周排期**
新建/打开版本 → 把已确认需求分配到版本 → 看需求数量、预估总工时 → 调整优先级和版本归属 → 导出本周计划。

**场景 E：验收与交付**
需求进入"待验收" → 逐条核对验收标准 → 标记完成 → 记录客户验收意见 → 导出项目需求清单和变更汇总。

**场景 F：复盘**
项目结束 → 对照原始基线和最终需求 → 看新增了多少、修改了多少、删除了多少、工期变化多少 → 形成复盘结论。

## 4. 产品原则

1. **需求是主线**：沟通、设计、排期、变更、验收都挂在需求上，而不是各建一套表。
2. **永不覆盖历史**：需求内容只追加版本，不物理删除。删除 = 取消，缩减 = 新版本 + 差异记录。
3. **变更分级**：
   - 澄清性修改（措辞、补充说明、验收标准细化）只记录版本，不强制走变更单；
   - 范围/工期/费用变化走正式变更单，记录原因、影响和客户确认。
4. **先记录，后规范**：小项目可以只记沟通和需求；流程复杂的项目再启用基线、变更审批、验收签收。
5. **给客户看的文档是一等公民**：需求清单、变更单、范围对比要能直接导出，而不是截图拼 Word。
6. **不造 Jira**：只做需求与交付的"账本"，研发执行细节留给代码仓库和任务工具。

## 5. 领域模型

### 5.1 概念关系

```
客户 Client
  └─ 项目 Project
       ├─ 需求 Requirement ── 需求版本 RequirementRevision
       │    ├─ 沟通记录 Communication（多对多）
       │    ├─ 变更项 ChangeItem ── 变更单 ChangeRequest
       │    ├─ 设计说明 / 设计链接
       │    └─ 验收记录 Acceptance（P1）
       ├─ 版本 / 里程碑 Release
       ├─ 沟通记录 Communication
       ├─ 变更单 ChangeRequest
       └─ 基线 Baseline（P1）
```

### 5.2 干系人 Stakeholder

| 字段 | 说明 |
| --- | --- |
| 名称 | 干系人姓名或组织名 |
| 公司 | 所属公司 / 组织，可选 |
| 联系方式 | 多条，类型为电话 / 微信 / 邮箱 / 其他，存 `stakeholder_contacts` |
| 备注 | 沟通偏好、关注点等 |
| 创建 / 更新时间 | 自动 |

干系人不是 CRM，只做项目归属和沟通对象记录，不做销售漏斗。项目与干系人是多对多关系，一个项目可以关联多个干系人，一个干系人也可以参与多个项目。

**角色属于“项目—干系人”关系，不属于干系人本身。** 同一个干系人在不同项目中可以承担不同角色，例如在 A 项目是决策人、在 B 项目是验收人。

### 5.3 项目 Project

| 字段 | 说明 |
| --- | --- |
| 干系人 | 可选，多选（0~N），通过 `project_stakeholders` 关联；每个关联可填写本项目角色 |
| 项目名称 | 必填 |
| 项目代号 | 用于需求编号前缀，如 `CRM`、`SHOP` |
| 简介 / 背景 | 可选 |
| 状态 | 洽谈中 / 待启动 / 进行中 / 暂停 / 已交付 / 已归档 |
| 开始日期 / 目标交付日期 | 可选 |
| 创建 / 更新时间 | 自动 |

### 5.4 需求 Requirement

需求是本应用的核心实体。

| 字段 | 说明 |
| --- | --- |
| 编号 | 自动生成，项目代号 + 序号，如 `CRM-001`，全局唯一、永不复用 |
| 所属项目 | 必填 |
| 父需求 | 可选，用于子功能/拆分（P1 完整支持，P0 预留字段） |
| 标题 | 必填，一句话说清要什么 |
| 需求描述 | 背景、目标、使用场景；Markdown |
| 验收标准 | 客户认可的完成条件，建议逐条列出 |
| 类型 | 功能 / 非功能 / 缺陷 / 优化 / 其他 |
| 来源 | 客户 / 自己 / 运营 / 技术 / 其他 |
| 优先级 | 高 / 中 / 低 |
| 状态 | 见 6.1 |
| 预估工时 | 人天，可空 |
| 所属版本 | 可选，未排期则为"待排期" |
| 设计说明 | 功能设计、交互说明、技术方案；Markdown |
| 设计链接 | Figma、文档、原型等 URL，多条 |
| 当前版本号 | 自动递增 |
| 确认版本 | 首次标记"已确认"时的版本快照，用于和当前内容对比 |
| 取消原因 | 需求被取消时必填 |
| 创建 / 更新时间 | 自动 |

**为什么编号要稳定**：客户沟通、变更单、导出文档都引用编号。编号随需求一生不变，标题可以改，编号不能改。

### 5.5 需求版本 RequirementRevision

每次需求内容发生实质变化时，保存一份快照，而不是覆盖原内容。

| 字段 | 说明 |
| --- | --- |
| 所属需求 | 必填 |
| 版本号 | 1、2、3… |
| 内容快照 | 标题、描述、验收标准、类型、优先级、预估、设计说明等字段的 JSON 快照 |
| 变更摘要 | 一句话说明这次改了什么 |
| 关联变更单 | 可选；正式变更必须关联 |
| 创建时间 | 自动 |

**记录时机**：
- 内容字段变化并保存时；
- 状态变化、版本归属变化等操作写入活动记录，不生成完整内容快照（避免版本爆炸）。

### 5.6 变更单 ChangeRequest 与变更项 ChangeItem

一次客户变更可能同时影响多条需求，所以用"变更单 + 变更项"的结构。

**变更单**：

| 字段 | 说明 |
| --- | --- |
| 编号 | 如 `CRM-CR-001` |
| 所属项目 | 必填 |
| 标题 | 一句话概括这次变更 |
| 变更原因 | 客户要求 / 政策变化 / 技术限制 / 自身优化… |
| 提出人 | 客户联系人、自己或其他人（自由文本） |
| 提出时间 | 日期 |
| 状态 | 草稿 / 评估中 / 待客户确认 / 已通过 / 已拒绝 / 已生效 / 已取消 |
| 范围影响 | 文字说明 |
| 工期影响 | 增减人天 |
| 费用影响 | 可选，金额 + 说明（不做财务系统） |
| 影响版本 | 可选 |
| 风险 / 依赖 | 可选 |
| 确认方式 | 微信 / 邮件 / 会议 / 书面签字 / 其他 |
| 确认时间 / 确认人 | 记录客户何时、由谁确认 |
| 确认备注 | 口头确认的上下文、证据说明 |

**变更项**：

| 字段 | 说明 |
| --- | --- |
| 所属变更单 | 必填 |
| 关联需求 | 必填（新增需求时可为空，生效后创建） |
| 变更类型 | 新增 / 修改 / 缩减范围 / 取消 / 拆分 / 合并 |
| 变更前快照 | JSON |
| 变更后快照 | JSON |
| 说明 | 本次针对该需求的具体变化 |

**变更类型说明**：

- **新增**：原来不存在的需求，变更生效后创建新需求；
- **修改**：标题、描述、验收标准、优先级、预估等发生变化；
- **缩减范围**：需求保留，但去掉其中一部分内容（"部分删除"的主要表达方式）；
- **取消**：整条需求不再需要，状态改为"已取消"，保留历史；
- **拆分 / 合并**：P1 支持，用于把一条大需求拆成多条子需求，或合并重复需求。

### 5.7 沟通记录 Communication

一条沟通记录是一个**沟通主题**，下挂多个**沟通场次**，用于支持会议、跨天续谈和多渠道沟通。

**沟通主题**

| 字段 | 说明 |
| --- | --- |
| 所属项目 | 必填 |
| 标题 | 沟通主题，例如“数据同步范围确认” |
| 状态 | 草稿 / 进行中 / 已完成 / 已归档 |
| 关联原始需求 | 可选，可关联多条 |
| 关联开发需求 | 可选，可关联多条 |
| 主题附件 | 可选，整体会议纪要、合同截图等 |
| 完成时间 / 归档时间 | 状态变更时记录 |

**沟通场次**

| 字段 | 说明 |
| --- | --- |
| 日期 | 本场沟通发生的日期 |
| 渠道 | 微信 / 会议 / 电话 / 邮件 / 其他 |
| 参与人 | 自由文本 |
| 沟通摘要 | 本场讨论了什么 |
| 结论 / 决定 | 本场确认了哪些事 |
| 待跟进 | 下一步要做什么、谁负责、何时 |
| 场次附件 | 微信截图、会议纪要、现场照片、PDF/Word 等 |

**设计要点**：

- 沟通记录不是聊天备份，而是“结论台账”；允许只写三行：讨论了什么、定了什么、下一步是什么。
- 使用独立整页编辑器，不使用会被点击遮罩关闭的弹框。
- 编辑内容自动保存，显示“保存中 / 已自动保存 / 保存失败”；返回或关窗前先落库。
- 跨天未结束时保持“进行中”，点“继续沟通/新增场次”新增一场，上一场内容保留。
- 归档代替物理删除；归档记录可恢复，已完成的记录可以重新打开。
- 附件支持文件选择、Ctrl+V 粘贴截图和拖拽文件；图片生成缩略图，其他文件调用系统程序打开；移除附件为软删除，文件不立即删除。

### 5.8 版本 / 里程碑 Release

| 字段 | 说明 |
| --- | --- |
| 所属项目 | 必填 |
| 名称 | 如 `V1.0`、`一期`、`2026-11 交付` |
| 目标 | 这个版本要交付什么 |
| 开始 / 结束日期 | 可选 |
| 状态 | 规划中 / 进行中 / 已发布 / 已归档 |
| 备注 | 可选 |

需求通过"所属版本"字段归属到版本。版本视图展示需求数量、预估总工时、按状态分布。**不做甘特图**，v1 只做列表 + 日期范围。

### 5.9 基线 Baseline（P1）

基线 = 某个时间点（合同确认、版本启动、客户验收）的需求集合快照。

- 项目可以有多条基线，如"合同基线""V1.0 基线"；
- 每条基线记录当时的需求编号、版本号和内容快照；
- 项目级"范围对比"：选择基线和当前状态，列出新增、修改、取消/缩减的需求。

**P0 的简化方案**：每条需求保存"确认版本"（首次确认时的快照），需求详情里可以对比"确认版本 vs 当前版本"。项目级基线放 P1。

### 5.10 验收 Acceptance（P1）

- 每条需求可维护验收标准清单；
- 记录验收结果（通过 / 不通过 / 部分通过）、验收人、验收时间、意见；
- 版本交付时汇总验收情况。

P0 先用"状态 + 验收备注"覆盖，不单独建验收单。

### 5.11 任务 Task（P1，非核心）

如果后续需要把需求拆成开发任务，再加任务实体（挂在需求下），但这不是本应用的重点。需求状态本身已经覆盖"开发中/待验收"。

## 6. 需求生命周期与变更模型

### 6.1 需求状态机

```
草稿 Draft
  → 澄清中 Clarifying
  → 已确认 Confirmed
  → 设计中 Designing
  → 已排期 Scheduled
  → 开发中 Developing
  → 待验收 Acceptance
  → 已完成 Done

任意状态 → 暂缓 OnHold → 回到之前状态
任意状态 → 已取消 Cancelled（需填原因）
```

说明：
- **草稿**：刚录入，还没和客户确认；
- **澄清中**：正在和客户沟通细节，可关联沟通记录；
- **已确认**：客户认可，记录确认版本，作为后续对比的基线；
- **设计中**：功能设计、交互设计、技术方案编写中；
- **已排期**：已分配到某个版本；
- **开发中**：进入实现；
- **待验收**：开发完成，等待客户验收；
- **已完成**：验收通过；
- **暂缓**：暂时不做，但有可能会回来；
- **已取消**：确定不做，保留历史。

状态允许自由切换，但切换到"已取消"必须填原因；从"已确认"之后修改内容，系统提示"这是澄清还是范围变更"。

### 6.2 两类修改，避免流程过重

| 类型 | 例子 | 是否走变更单 | 记录方式 |
| --- | --- | --- | --- |
| 澄清性修改 | 补充描述、细化验收标准、修正错别字 | 否 | 生成新需求版本 |
| 范围变更 | 新增功能、删除功能、改验收标准导致工作量变化 | 是 | 变更单 + 需求版本 |

**判断规则（建议）**：
- 只改描述措辞、补充说明 → 澄清；
- 改验收标准、改变功能边界、改优先级导致排期变化 → 范围变更；
- 拿不准时，保存时弹窗让用户选，默认建议"范围变更"。

这个设计是为了解决一个矛盾：如果每次编辑都强制走变更单，你会嫌烦而不记录；如果都不走，历史又会丢。分级是折中。

### 6.3 "部分删除"怎么表达

这是需求变更里最容易做错的地方。分三种情况：

1. **整条需求不要了**
   - 需求状态改为"已取消"，填写取消原因；
   - 变更项类型 = "取消"；
   - 需求仍保留在台账和历史里，默认视图可过滤掉。

2. **需求还在，但其中一部分不要了**
   - 修改需求描述和验收标准，删掉那部分内容；
   - 变更项类型 = "缩减范围"；
   - 系统保存修改前后的快照，差异视图能看出删了哪几句；
   - 这是 P0 必须支持的"部分删除"。

3. **需求由多个子项组成，只删其中一个子项**
   - 把需求拆成父子结构，取消其中一个子需求；
   - 需要需求层级和拆分功能，放 P1；
   - P0 可以先用第 2 种方式（把子项写在验收标准/描述里，撤销时改文本）过渡。

**原则：永远不物理删除需求。** 客户三个月后问"当时那个功能呢"，你还能翻出来。

### 6.4 原始需求（合同范围）vs 开发需求

- **原始需求**：客户提供的 Excel 范围表，按“来源文件 → 模块 → 子项”导入，保留原始描述和 Excel 行号；作为合同范围基线，导入后锁定，不直接设计、排期或开发。
- **开发需求**：当前需求台账，由原始需求细化而来，或来自沟通记录、直接创建；承载验收标准、设计说明、预估、状态和实际开发日期。
- **来源文件**：一个项目可以导入多份 Excel（初始范围、补充清单、合同变更附件），每份文件有独立编号（SRC-01、SRC-02…）和版本；没有 Excel 时也可以直接手工新建原始需求，归入“手工录入原始需求”来源文件。
- **来源关系**：原始需求与开发需求是多对多，一个原始项可以拆成多个开发需求，一个开发需求也可以覆盖多个原始项。
- **覆盖状态**：原始需求列表自动显示已关联的开发需求；没有关联的标为“未细化”，用于检查合同范围是否漏项。

开发需求有三个来源：

1. **原始需求**：必须关联至少一条原始需求；沟通记录可以作为细化依据另行关联。
2. **沟通记录**：必须选择一条来源沟通记录；如果补充内容属于原合同范围，可以再关联原始需求。
3. **直接创建**：不强制关联，适合内部改进、技术任务等场景。

`origin` 记录“最早从哪里来”，原始需求关联和沟通关联记录“覆盖/讨论了什么”，两者分开。

### 6.5 变更影响与确认

变更单不是审批流引擎，重点是把"为什么改、改了什么、影响多少、客户是否同意"记清楚。

- 影响范围：文字 + 受影响需求列表；
- 工期影响：增减人天，用于排期参考；
- 费用影响：可选；
- 客户确认：方式、时间、确认人、备注；
- 生效：点击"应用变更"，系统批量更新需求内容/状态，并生成新版本；
- 生效后不可反向修改历史，只能再发一次变更。

## 7. 功能清单与优先级

优先级：**P0 = MVP 必须做**；**P1 = 首版后尽快做**；**P2 = 有明确需求再做**。

### 7.1 P0：MVP

#### ① 客户与项目

- 客户增删改查；
- 项目增删改查，关联客户，项目代号用于需求编号；
- 项目状态、起止日期、简介；
- 项目列表与筛选。

#### ② 需求台账

- 导入客户 Excel 作为原始需求/合同范围基线，保留模块、子项、描述和源行号；支持多份来源文件和版本；
- 支持手工新建原始需求，归入“手工录入原始需求”来源文件；
- 原始需求列表显示覆盖状态，可查看已关联的开发需求；
- 开发需求来源分为原始需求、沟通记录、直接创建；原始需求来源必须关联原始需求，沟通记录来源必须关联沟通记录；
- 新建需求：标题必填，其余可选；自动生成编号；
- 需求列表：表格视图，展示编号、标题、类型、优先级、状态、版本、预估、更新时间；
- 筛选：项目、状态、类型、优先级、版本、来源；
- 搜索：编号、标题、描述；
- 排序：编号、更新时间、优先级、预估；
- 行内快速修改状态和优先级；
- 批量粘贴创建：粘贴多行文本，每行生成一条草稿需求（降低初始录入成本）；
- 需求详情编辑：描述、验收标准、设计说明、设计链接、预估、版本；
- 需求状态流转，取消时必须填原因。

**验收**：新建项目后 5 分钟内能录入 20 条需求；列表筛选组合正确；编号不重复、不复用。

#### ③ 需求版本与差异

- 每次保存内容修改时自动生成版本，记录变更摘要；
- 需求详情展示版本历史；
- 任选两个版本进行对比，标出新增/删除/修改的文字；
- 展示"确认版本 vs 当前版本"的差异。

**验收**：修改需求描述后，旧内容仍能在历史中找回；差异视图能准确标出删除的句子。

#### ④ 沟通记录

- 新建沟通记录：项目、时间、渠道、参与人、摘要、结论、待跟进；
- 关联一条或多条需求；
- 按项目/需求查看沟通记录；
- 需求详情页展示相关沟通记录；
- 工作台展示最近沟通。

**验收**：能从需求详情看到"这条需求是在哪次沟通中确认的"；沟通记录可以独立于需求存在（项目级沟通）。

#### ⑤ 变更管理

- 新建变更单：标题、原因、提出人、影响（范围/工期/费用/版本/风险）；
- 添加变更项：选择需求、变更类型、修改前后内容；
- 新增需求的变更项：填写新需求内容，生效后创建需求；
- 变更单状态流转：草稿 → 评估中 → 待客户确认 → 已通过/已拒绝 → 已生效；
- 记录客户确认方式、时间、确认人；
- 应用变更：批量更新需求，生成新版本；
- 变更单列表与详情，展示受影响的全部需求；
- 取消变更单：未生效的可以取消。

**验收**：一次变更能同时影响多条需求；应用变更后需求历史完整；拒绝的变更不会改动需求。

#### ⑥ 版本与排期

- 版本的增删改查：名称、目标、起止日期、状态；
- 把需求分配到版本，或从版本移回"待排期"；
- 版本视图展示需求数量、预估总工时、按状态分布；
- 项目详情中展示版本列表。

**验收**：需求在版本间移动后，两个版本的统计同步更新；预估总工时计算正确。

#### ⑦ 工作台

- 待确认需求：状态为草稿/澄清中的需求；
- 待处理变更：评估中/待客户确认的变更单；
- 即将到期版本：结束日期临近的版本；
- 最近沟通、最近变更；
- 快速入口：新建需求、新建沟通、新建变更。

#### ⑧ 导出与数据

- 导出需求清单（按项目/版本/筛选结果）为 Markdown 或 CSV；
- 导出变更单为 Markdown；
- 导出项目范围对比（P0 简化版：确认版本 vs 当前版本的逐条差异，P1 再做项目级汇总）；
- SQLite 本地存储，自动迁移；
- 每日自动备份，保留 7 份；
- 导入/导出全部数据 JSON；
- 设置页：数据目录、备份目录、主题、版本信息。

**验收**：导出的 Markdown 可以直接发给客户；备份文件能恢复；数据库损坏时能从备份重建。

#### ⑨ 应用基础

- 侧边栏：工作台 / 项目 / 需求 / 变更 / 版本 / 客户 / 设置；
- 全局搜索（项目、需求编号/标题）；
- 中文界面，浅色/深色/跟随系统；
- 快捷键：`Ctrl+N` 新建需求，`Ctrl+K` 全局搜索，`Esc` 关闭弹层；
- 窗口大小与位置记忆；
- 空状态、错误提示、删除确认。

### 7.2 P1：首版之后

- **项目级基线**：创建基线、基线列表、范围对比（新增/修改/取消/缩减）；
- **需求层级与拆分/合并**：父子需求、拆分、合并、批量移动；
- **验收管理**：验收标准清单、逐条勾选、验收结果、客户签收记录；
- **客户交付文档**：需求确认单、变更单、范围对比、项目进度报告，支持打印/PDF；
- **附件**：沟通截图、会议纪要、合同、原型文件，复制到应用数据目录；
- **看板视图**：需求按状态分列，拖拽改状态；
- **批量操作**：批量改状态/版本/优先级、批量导出；
- **保存筛选视图**：常用筛选组合保存为快捷入口；
- **提醒**：待确认需求超期、变更待确认超期、版本临近截止；
- **任务拆分**：需求下挂开发任务（可选）；
- **AI 辅助**：把沟通记录整理成需求草稿/变更草稿、生成周报（需明确数据去向）；
- **导入**：从 CSV/Excel 导入初始需求列表。

### 7.3 P2：按需再做

- 多人协作、角色权限、评论
- 客户端门户（客户查看/确认需求）
- 云同步、多设备
- GitHub/GitLab/飞书/钉钉集成
- 合同、报价、回款
- 甘特图、依赖关系、资源排期
- 测试用例、缺陷跟踪、发布管理
- 移动端

### 8.2 主要页面

1. **工作台**：待确认需求、待处理变更、临近版本、最近沟通、最近变更。
2. **项目列表**：客户、状态、需求数、当前版本、最近更新。
3. **项目详情**：概览 + 标签页（开发需求 / 沟通记录 / 版本 / 变更 / 活动）。
4. **需求台账**：全局或项目内，表格视图、筛选、搜索、批量操作。
5. **需求详情**：
   - 顶部：编号、标题、状态、优先级、所属版本；
   - 内容区：描述、验收标准、设计说明、设计链接；
   - 侧栏：类型、来源、预估、父需求、创建/更新时间；
   - 标签页：版本历史 / 沟通记录 / 变更记录 / 活动。
6. **变更中心**：全部变更单，按状态/项目筛选；详情页展示变更项、前后差异、影响、客户确认、应用按钮。
7. **版本计划**：版本列表 → 版本详情（需求清单、预估合计、状态分布）。
8. **客户列表**：客户及其项目。
9. **设置**：数据目录、备份、主题、导出/导入。

### 8.3 关键交互约定

- **新建需求**：只强制标题；编号自动生成；`Enter` 保存，`Shift+Enter` 换行；保存后保持列表位置。
- **批量粘贴**：粘贴多行文本 → 预览 → 每行一条草稿需求 → 批量保存。
- **保存已确认需求**：如果内容字段变化，弹出选择"澄清性修改"或"范围变更"；选择范围变更时引导创建变更单。
- **取消需求**：必须填原因；默认从列表隐藏，可通过筛选查看。
- **应用变更**：先展示受影响需求和新旧差异，确认后批量应用；应用后变更单锁定，不可再改。
- **删除**：项目/需求优先引导归档/取消；永久删除仅限草稿，且需二次确认。
- **导出**：从当前筛选结果直接导出，所见即所得。

## 9. 关键流程

### 9.1 初始需求整理

```
新建客户 → 新建项目（填写代号）
  → 批量粘贴客户需求列表
  → 逐条进入"澄清中"，记录沟通、补充验收标准
  → 客户确认后标记"已确认"（记录确认版本）
  → 形成项目初始范围
```

### 9.2 客户提出新需求

```
新建变更单（类型：新增）
  → 填写原因、提出人
  → 添加变更项：填写新需求内容、预估、影响版本
  → 评估影响（范围/工期/费用）
  → 记录客户确认方式和时间
  → 状态改为"已通过" → 应用变更
  → 系统创建新需求，编号自动生成
  → 需求进入待排期
```

### 9.3 客户修改/部分删除需求

```
打开原需求 → 发起变更（类型：修改/缩减范围）
  → 编辑需求描述和验收标准（删除不要的部分）
  → 系统生成变更前后快照
  → 填写变更原因、影响工期
  → 客户确认后应用变更
  → 需求生成新版本，历史保留
  → 基线对比显示"缩减范围"
```

### 9.4 排期

```
新建版本（名称、目标、起止日期）
  → 从"待排期"需求中选择并分配
  → 查看需求数量、预估总工时、状态分布
  → 调整优先级和版本归属
  → 需求状态变为"已排期"
  → 导出本周计划
```

### 9.5 验收与交付

```
需求开发完成 → 状态"待验收"
  → 逐条核对验收标准（P0：备注；P1：清单）
  → 记录客户验收意见
  → 状态"已完成"
  → 版本状态"已发布"
  → 导出需求清单 + 变更汇总 + 范围对比
```

## 10. 技术方案建议

沿用你现有项目的技术栈，降低学习和搭建成本：

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 桌面框架 | Tauri 2 | 复用 `task_manager` 的工程骨架与发布流程 |
| 前端 | Vue 3 + TypeScript + Vite | 与你现有项目一致 |
| UI | Tailwind CSS v4 + shadcn-vue + reka-ui + lucide-vue | 表格、表单、弹窗组件现成 |
| 状态管理 | Pinia | 项目、需求、变更等工作区状态 |
| 路由 | vue-router | 工作台/项目/需求/变更/版本/客户/设置 |
| 数据库 | SQLite，`@tauri-apps/plugin-sql` | 关系型数据、事务、迁移都更合适 |
| 系统能力 | `plugin-opener`、`plugin-dialog`、`plugin-fs` | 打开链接、选择导出路径、备份 |
| 文本差异 | `diff` 库 | 需求版本对比、变更前后对比 |
| Markdown | 轻量渲染器 + 编辑器 | 需求描述、沟通摘要、设计说明 |
| 测试 | Vitest | 重点测变更应用、版本快照、筛选逻辑 |
| 打包 | GitHub Actions + `tauri build` | 参考 `task_manager` |

**不推荐**：Electron（包体大）、自建本地 Web 服务（多余）、重型 ORM（表结构不复杂，手写 SQL 更可控）、一开始就做多用户和权限。

### 10.1 数据设计要点

- 需求内容快照用 JSON 存，字段变化不用频繁改表结构；同时保留常用查询字段为独立列（状态、优先级、版本、项目）。
- 变更应用必须在一个事务里完成：写需求新内容、生成版本、更新变更项状态、写活动记录。
- 需求编号按项目前缀 + 自增序号生成，序号存在项目表里，避免并发/删除导致复用。
- 所有"删除"优先软删除（归档/取消），真正的物理删除只允许草稿且二次确认。
- 每日备份用 SQLite 文件复制；恢复前先备份当前库。

### 10.2 建议目录结构

```
src/
  views/          Dashboard / Projects / Requirements / Changes / Releases / Clients / Settings
  components/     requirements/ changes/ releases/ communications/ ui/ layout/
  stores/         projects.ts requirements.ts changes.ts releases.ts settings.ts
  db/             database.ts migrations.ts repositories/
  composables/    useDiff.ts useExport.ts useShortcuts.ts
  lib/            ids.ts dates.ts markdown.ts
src-tauri/        窗口配置、SQL 迁移注册、备份命令
```

## 11. 非功能需求

- **性能**：单项目 1000 条需求下列表/筛选流畅；版本对比 5000 字文本无明显卡顿；冷启动 < 2 秒。
- **数据安全**：SQLite WAL；变更应用使用事务；每日备份保留 7 份；导出/恢复前二次确认。
- **离线**：核心功能完全离线；默认不发起网络请求。
- **可追溯**：需求版本、变更、沟通、状态变化都有时间戳；关键操作写活动记录。
- **可导出**：所有客户交付物都能导出为通用格式（Markdown/CSV/HTML），不锁定在应用内。
- **跨平台**：Windows 优先，路径和快捷键按跨平台设计。
- **主题与可访问性**：浅色/深色/跟随系统；键盘可完成主要操作；对比度达标。
- **国际化**：文案集中管理，默认中文。
- **隐私**：不收集遥测；客户信息只存在本地；AI 功能默认关闭并明确数据去向。

## 12. 里程碑建议

| 阶段 | 内容 | 预计（每天 2~4 小时） |
| --- | --- | --- |
| M0 模型与线框 | 确认本文档、定稿 schema、画工作台/需求列表/需求详情/变更详情四张线框 | 3~5 天 |
| M1 骨架与基础数据 | Tauri 工程、路由布局、SQLite 迁移、客户/项目 CRUD | 4~6 天 |
| M2 需求台账 | 需求列表、筛选搜索、新建/编辑、批量粘贴、编号生成 | 1.5~2 周 |
| M3 版本历史与差异 | 需求版本快照、版本历史、两版本 diff、确认版本对比 | 1 周 |
| M4 沟通与变更 | 沟通记录、变更单/变更项、应用变更、客户确认 | 1.5~2 周 |
| M5 版本排期与工作台 | 版本 CRUD、需求分配、工时统计、工作台聚合 | 1 周 |
| M6 导出与发布 | Markdown/CSV 导出、备份、设置、打包验证、首个 Release | 1 周 |
| M7 自用打磨 | 用真实项目跑两周，修交互问题，再决定 P1 | 持续 |

**总工期预估：7~9 周**（每天 2~4 小时）。如果只有周末，按 3~4 个月规划。

**重要建议**：先做一个"垂直切片"——客户/项目 + 需求台账 + 版本历史 + 变更单，用你自己的一个真实项目跑通。版本排期、导出、工作台可以在切片验证后再做。不要按页面顺序开发，要按"一条需求从录入到变更生效"的完整链路开发。

## 13. 风险与对策

| 风险 | 表现 | 对策 |
| --- | --- | --- |
| 范围膨胀 | 想做完 Jira 的所有功能，首版永远出不来 | 锁死 P0；牢记"只做需求与变更台账" |
| 模型过重 | 版本、变更单、基线、验收概念太多，自己都不想用 | 分级：小项目只用需求和沟通；复杂项目才启用变更单/基线 |
| 录入疲劳 | 沟通记录和变更单变成额外负担 | 快速录入模板；允许只写三行；批量粘贴；每周固定整理 |
| 变更流程和实际不符 | 客户只在微信口头确认，不愿签字 | 确认方式支持"微信+截图+备注"，不强制正式审批 |
| 版本历史混乱 | 每次保存都生成版本，历史爆炸 | 只有内容字段变化才生成版本；状态变化走活动记录 |
| 部分删除表达不清 | 直接改文本，历史丢失 | 强制保留前后快照；P1 加需求层级和拆分 |
| 客户交付文档不专业 | 导出格式粗糙，客户看不懂 | 导出模板固定：编号、标题、描述、验收标准、状态、变更说明 |
| 新手踩坑 | Tauri 插件、SQLite 迁移、打包 | 复用现有项目；每个里程碑打包一次；先跑通一条链路 |
| 项目烂尾 | 它成为第 N 个未完成项目 | 7~9 周硬性 MVP；先用真实项目跑两周再扩展 |

## 14. 待确认问题

以下问题会直接改变数据模型和 MVP 范围，建议优先讨论：

1. **你的实际角色和协作方式**
   - 是个人接客户项目，还是小团队/公司内部产品？
   - 同时维护几个项目？客户会登录系统，还是你导出文档给他们？
   - 只有你一个人用，还是团队其他人也要用？

2. **"排期"的粒度**
   - 按版本/里程碑（几周一个）就够，还是需要按周迭代、甚至排到具体某一天？
   - 需要工时预估、人力容量、费用换算吗？
   - 需要甘特图/依赖关系，还是列表 + 日期范围就够？

3. **变更的正式程度**
   - 客户通常怎么确认：微信口头、邮件、会议纪要，还是书面变更单？
   - 需要保存截图/附件作为证据吗？
   - 变更单是"给自己看的记录"，还是"要发给客户签字确认"的文档？

4. **"部分删除"的具体例子**
   - 是删除一条需求里的某个验收点？
   - 还是删除一个子功能/子模块？
   - 还是把一条大需求拆成几条，然后删掉其中一条？
   - 这决定 P0 要不要直接做需求层级（父子需求）。

5. **功能设计的深度**
   - 只需要在需求里写设计说明 + 放链接（Figma/文档）？
   - 还是需要管理原型文件、设计稿版本、附件？
   - 设计是否需要单独审批/确认？

6. **验收和交付物**
   - 需要逐条验收标准勾选、客户签收吗？
   - 需要导出哪些文档：需求确认单、变更单、范围对比、进度报告？
   - 格式要求：Markdown/Excel 够用，还是必须 PDF/Word？

7. **现有资料**
   - 你现在的需求列表是什么格式（Excel/Word/微信/脑图）？
   - 首版是否需要从 Excel/CSV 批量导入？

## 附录：数据库 schema 草案

```sql
CREATE TABLE stakeholders (
  id          TEXT PRIMARY KEY,
  name        TEXT NOT NULL,
  company     TEXT,
  notes       TEXT NOT NULL DEFAULT '',
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL
);

CREATE TABLE stakeholder_contacts (
  id             TEXT PRIMARY KEY,
  stakeholder_id TEXT NOT NULL REFERENCES stakeholders(id) ON DELETE CASCADE,
  type           TEXT NOT NULL DEFAULT 'phone', -- phone / wechat / email / other
  value          TEXT NOT NULL,
  sort_order     INTEGER NOT NULL DEFAULT 0,
  created_at     TEXT NOT NULL
);

CREATE TABLE projects (
  id             TEXT PRIMARY KEY,
  name           TEXT NOT NULL,
  code           TEXT NOT NULL UNIQUE,       -- 需求编号前缀，如 CRM
  description    TEXT NOT NULL DEFAULT '',
  status         TEXT NOT NULL DEFAULT 'active'
                 CHECK (status IN ('negotiating', 'pending_start', 'active', 'paused', 'delivered', 'archived')),
  start_date     TEXT,
  target_date    TEXT,
  req_seq        INTEGER NOT NULL DEFAULT 0, -- 需求编号自增序号
  cr_seq         INTEGER NOT NULL DEFAULT 0, -- 变更单编号自增序号
  created_at     TEXT NOT NULL,
  updated_at     TEXT NOT NULL
);

CREATE TABLE project_stakeholders (
  project_id     TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  stakeholder_id TEXT NOT NULL REFERENCES stakeholders(id) ON DELETE CASCADE,
  role           TEXT,                         -- 本项目中的角色，自由文本
  PRIMARY KEY (project_id, stakeholder_id)
);

CREATE TABLE requirements (
  id                  TEXT PRIMARY KEY,
  project_id          TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  parent_id           TEXT REFERENCES requirements(id) ON DELETE SET NULL,
  depth               INTEGER NOT NULL DEFAULT 0, -- 0 需求 / 1 模块 / 2 子功能
  code                TEXT NOT NULL UNIQUE,  -- CRM-001
  title               TEXT NOT NULL,
  description         TEXT NOT NULL DEFAULT '',
  acceptance_criteria TEXT NOT NULL DEFAULT '',
  design_notes        TEXT NOT NULL DEFAULT '',
  design_links        TEXT NOT NULL DEFAULT '', -- JSON 数组
  type                TEXT NOT NULL DEFAULT 'feature'
                      CHECK (type IN ('feature', 'non_functional', 'bug', 'improvement', 'other')),
  source              TEXT NOT NULL DEFAULT 'client'
                      CHECK (source IN ('client', 'self', 'operation', 'tech', 'other')),
  priority            INTEGER NOT NULL DEFAULT 1, -- 0 低 / 1 中 / 2 高
  status              TEXT NOT NULL DEFAULT 'draft'
                      CHECK (status IN ('draft', 'clarifying', 'confirmed', 'designing',
                                        'scheduled', 'developing', 'acceptance', 'done',
                                        'on_hold', 'cancelled')),
  estimate_days       REAL,
  release_id          TEXT REFERENCES releases(id) ON DELETE SET NULL,
  current_revision_no INTEGER NOT NULL DEFAULT 0,
  baseline_revision_no INTEGER,              -- 首次确认时的版本号
  confirmed_at        TEXT,
  dev_started_at      TEXT,                  -- 第一次进入"开发中"
  dev_completed_at    TEXT,                  -- 最近一次进入"已完成"
  cancelled_at        TEXT,
  cancel_reason       TEXT,
  sort_order          INTEGER NOT NULL DEFAULT 0,
  created_at          TEXT NOT NULL,
  updated_at          TEXT NOT NULL
);

CREATE INDEX idx_requirements_project ON requirements(project_id);
CREATE INDEX idx_requirements_status ON requirements(status);
CREATE INDEX idx_requirements_release ON requirements(release_id);

CREATE TABLE requirement_revisions (
  id                TEXT PRIMARY KEY,
  requirement_id    TEXT NOT NULL REFERENCES requirements(id) ON DELETE CASCADE,
  revision_no       INTEGER NOT NULL,
  snapshot_json     TEXT NOT NULL,           -- 标题/描述/验收标准/设计/类型/优先级/预估
  change_summary    TEXT NOT NULL DEFAULT '',
  change_request_id TEXT REFERENCES change_requests(id) ON DELETE SET NULL,
  created_at        TEXT NOT NULL,
  UNIQUE (requirement_id, revision_no)
);

CREATE TABLE releases (
  id          TEXT PRIMARY KEY,
  project_id  TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  name        TEXT NOT NULL,
  goal        TEXT NOT NULL DEFAULT '',
  start_date  TEXT,
  end_date    TEXT,
  status      TEXT NOT NULL DEFAULT 'planning'
              CHECK (status IN ('planning', 'in_progress', 'released', 'archived')),
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL
);

CREATE TABLE change_requests (
  id                TEXT PRIMARY KEY,
  project_id        TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  code              TEXT NOT NULL UNIQUE,    -- CRM-CR-001
  title             TEXT NOT NULL,
  reason            TEXT NOT NULL DEFAULT '',
  requested_by      TEXT,
  requested_at      TEXT,
  status            TEXT NOT NULL DEFAULT 'draft'
                    CHECK (status IN ('draft', 'assessing', 'pending_client',
                                      'approved', 'rejected', 'applied', 'cancelled')),
  impact_scope      TEXT NOT NULL DEFAULT '',
  impact_days       REAL,
  impact_cost       REAL,
  impact_cost_note  TEXT,
  affected_release_id TEXT REFERENCES releases(id) ON DELETE SET NULL,
  risk_note         TEXT NOT NULL DEFAULT '',
  confirm_channel   TEXT,
  confirmed_by      TEXT,
  confirmed_at      TEXT,
  confirm_note      TEXT,
  applied_at        TEXT,
  created_at        TEXT NOT NULL,
  updated_at        TEXT NOT NULL
);

CREATE TABLE change_items (
  id                TEXT PRIMARY KEY,
  change_request_id TEXT NOT NULL REFERENCES change_requests(id) ON DELETE CASCADE,
  requirement_id    TEXT REFERENCES requirements(id) ON DELETE SET NULL,
  change_type       TEXT NOT NULL
                    CHECK (change_type IN ('add', 'modify', 'reduce', 'cancel', 'split', 'merge')),
  before_json       TEXT,
  after_json        TEXT,
  note              TEXT NOT NULL DEFAULT '',
  created_at        TEXT NOT NULL
);

CREATE TABLE communications (
  id          TEXT PRIMARY KEY,
  project_id  TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  occurred_at TEXT NOT NULL,
  channel     TEXT NOT NULL DEFAULT 'meeting'
              CHECK (channel IN ('wechat', 'meeting', 'phone', 'email', 'other')),
  participants TEXT NOT NULL DEFAULT '',
  summary     TEXT NOT NULL DEFAULT '',
  decisions   TEXT NOT NULL DEFAULT '',
  follow_ups  TEXT NOT NULL DEFAULT '',
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL
);

CREATE TABLE communication_requirements (
  communication_id TEXT NOT NULL REFERENCES communications(id) ON DELETE CASCADE,
  requirement_id   TEXT NOT NULL REFERENCES requirements(id) ON DELETE CASCADE,
  PRIMARY KEY (communication_id, requirement_id)
);

CREATE TABLE activities (
  id          TEXT PRIMARY KEY,
  entity_type TEXT NOT NULL,                 -- requirement / project / change / release
  entity_id   TEXT NOT NULL,
  action      TEXT NOT NULL,                 -- status_changed / release_changed / created ...
  detail_json TEXT,
  created_at  TEXT NOT NULL
);
```
